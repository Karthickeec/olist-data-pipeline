# Salting demo: skew on customer_state

Generated by `make salting-demo` (`scripts/salting_demo.py`). Setup: Spark 3.5.9 on this laptop, `local[2]`, 2 GB driver, 8 shuffle partitions, salt factor 8. The input is `gold.fact_order_lines` (orders through 2017-12-31) replicated ×100, giving 5,123,400 rows. Replicating keeps the state mix: SP 39.4%, RJ 13.8%, MG 12.1%, RS 5.9%.

## Where the rows go

Rows per shuffle partition when hashing on `customer_state` (the plain queries): `[212200, 0, 259300, 926400, 2513400, 710700, 179800, 321600]`. The largest partition holds 49% of all rows. Hashing on `(customer_state, salt)` gives `[591991, 334689, 763324, 748465, 993888, 669058, 833948, 188037]`, and the largest holds 19%.

## What the numbers say

- **(a) sum+count by state**, AQE off: wall 0.46s → 0.69s, busiest task reads 82 → 431 rows and runs 2 → 5 ms.
  - Spark pre-aggregates each input partition before the shuffle, so every state sends only one row per partition.
  - The skew never reaches the shuffle, and salting just adds a second aggregation.
  - **Don't salt combinable aggregations** (sum, count, min, max, avg).
  - The same goes for `countDistinct`, which Spark shuffles by (key, value), and for `row_number() <= N`
    windows, where Spark 3.5 applies a per-partition limit before the shuffle (WindowGroupLimit).
- **(b) sort-merge join on state**, AQE off: wall 2.58s → 3.18s, busiest task reads 2,513,403 → 993,913 rows and runs 1707 → 747 ms.
  - In a sort-merge join every row of a key goes to one task, so SP's 39% of the rows lands on a single task.
  - Salting the big side and replicating the small side ×N spreads SP over N tasks.
  - The cost is 8× more rows on the small side, plus an extra column.
- **AQE with skew-join handling** (thresholds lowered to suit laptop data): plain join wall 2.38s, busiest task 522,003 rows / 337 ms (vs 2,513,403 rows / 1707 ms with AQE off).
  - AQE split the skewed partition: the join stage ran 25 tasks instead of 8, with no code change.
  - AQE splits the skewed partition at runtime and replicates the matching partition of the other side.
  - Gotcha found while building this demo: AQE's skew-join rule needs a shuffle on *both* sides.
    The first version cached the small side straight from a `groupBy(customer_state)`, so it was already
    hash-partitioned on the key and Spark skipped its shuffle. AQE then left the skewed join alone
    (no `AQEShuffleRead` in the plan), even with `forceOptimizeSkewedJoin`.
  - That is the same idea as salting, done automatically. On Spark 3.x, AQE skew joins are the first tool;
    manual salting is for when AQE can't apply (the skew is under its thresholds, a non-join operator, or older Spark).
- **Why the timings move less than the row counts**:
  - `local[2]` has two cores, so balancing can speed things up at most about 2×.
  - At 5,123,400 rows the stages take milliseconds, and fixed costs dominate.
  - The row counts show the effect directly: the busiest join task reads 2,513,403 rows plain and 993,913 salted.
  - On a cluster with dozens of executors and a skewed key of hundreds of GB, that busiest task is the job's runtime.
